# iPhone RN + nRF52840 DK: pending ATT read abort/expiry feasibility

Date: 2026-09-27. Status: **isolated RF feasibility passes for held-read ABORT, EXPIRED, BTP control-session close/reopen while WAITING, and a same-host two-generation RN engine-reload gate**, followed by fresh-connection RELEASE reads. The latest reload candidate additionally observed native `dispose()` return and rejection of a test-only synthetic old-read submission to the closed sink. This is not physical USB loss, a full `rf-io` pass, an actual CoreBluetooth late-callback proof, proof that callbacks already handed to Nitro drained, or a maintained production-provider pass. The earlier [initial-read report](2026-09-27-react-native-ios-dk-pending-att-initial-read.md) identifies the candidate, J-Link flash limits and successful RELEASE boundary.

## Mechanism and controls

The isolated [`run_dk_initial_read.py`](../../../spikes/archive/nrf-att-hold/run_dk_initial_read.py) owns one exclusive 115200 8N1 hardware-flow-control BTP serial session on the physically observed DK VCOM. It provisions a diagnostic service `fd100000-0000-4000-8000-000000000000` with the target read-write value at handle `41` and permissions `0x43`. Its `--action abort` and `--action expire` modes require an exact `WAITING` snapshot and an immediate second STATUS before applying the fault. It polls for the exact firmware terminal (`ABORTED` or `EXPIRED`) with a monotonic deadline and independently requires the RN event stream to report a `commandCompleted.error:9010:permission` initial-read failure after matching GATT discovery. Neither firmware state alone nor UI text alone is an RF result.

The runner's pre-existing `rf-io` mode is only a trigger and event sink for the **first** read. It attempts later reads that the one-shot diagnostic characteristic is not required to authorize. A nonzero underlying `rf-io` runner exit is expected and is not reported as a full I/O pass. The isolated script returns success only for its own selected first-read boundary, then re-arms once in the same BTP session, verifies old RELEASE and ABORT generation controls both fail with BTP status `01`, verifies the fresh arm stayed `ARMED`, and aborts that unused arm. Its attempt and console logs are ignored local files under `.work/nrf-att-hold-dk/`; newer attempts use UUID-separated paths so retries cannot overwrite earlier evidence.

## Locked-device transport-loss attempt (not RF evidence)

An explicitly isolated `--action transport-loss` attempt was made. `devicectl` refused to launch the RN app because the iPhone was locked (`BSErrorCodeDescription = Locked`); the runner exited **2** before any read entered `WAITING`, aborted its unused ARM, and removed its owned lock. Its ignored attempt/runner logs are kept under `.work/nrf-att-hold-dk/rn-first-read-transport-loss.*.log`. This is neither a transport-loss pass nor a callback failure. The runner now reports the locked-device reason directly rather than a misleading missing-ATT-callback error.

A separate **BTP-only** check closed the exclusive serial session while not holding any ATT read, reopened the same VCOM, and observed identical `ABORTED` state and `(sequence=1, handle=41)` before/after reopening. It proves the idle VCOM close/reopen did not erase that observed hold state; it does not establish how the state came to be sequence 1, nor what happens when the callback is blocked. The iPhone was subsequently unlocked (`devicectl lockState`: `passcodeRequired=false`, `unlockedSinceBoot=true`). Two subsequent unlocked RN launches scanned and found the DK advertisement but reported `rf:step:connected:failed:connectionStateChanged.err:connection:CoreBluetooth failed to connect to the peripheral`. Both were before `WAITING` and had their unused arms aborted; neither is transport-loss evidence.

That failed RN attempt's ignored log is `.work/nrf-att-hold-dk/rn-first-read-release-b0651d5a98634bf0ba5cb9a4a10e7c82.attempt.log`, with `.runner.log` alongside it. ## Native connection error and human pairing cleanup

The internal RN host previously rendered only the normalized `BleEventError.message` for connect failures, even though the production Apple backend already propagates the `NSError` domain and code through `platformDetails`. A private host-only failure marker now appends the native domain/code (without peer address); TypeScript and a quiet incremental signed iPhone app build passed. The first bounded `release` run of that exact new app again scanned the diagnostic service and then failed before ATT `WAITING` with `connectionStateChanged.err:connection:CoreBluetooth failed to connect to the peripheral:native=CBErrorDomain/14`. The bounded BTP capture window saw `connected=0,disconnected=0`; its unused arm was aborted and there was no residual fixture lock. Attempt log: `.work/nrf-att-hold-dk/rn-first-read-release-5d3d2326db2a4f27ba02a0ba036672a1.attempt.log`.

The locally installed Apple iPhoneOS 27.0 SDK's `CoreBluetooth.framework/Headers/CBError.h` maps **`CBError` 14** to **`CBErrorPeerRemovedPairingInformation`** (distinct from connection timeout `6` and generic connection failure `10`). This identifies the native error code, not a proven specific mechanism in the DK. An old iPhone pairing/bond for this fixture after firmware/identity changes is a plausible cause. A human must identify the **exact DK** in iPhone Settings → Bluetooth (the fixture profile's scan-response name is `BleHubNrf52840`, though iOS may display a different cached name) and, if present, choose “Forget This Device”; do not clear unrelated pairings. Then keep the iPhone unlocked and retry the `release` baseline. If there is no matching entry, or the error persists, investigate iOS pairing state and DK settings separately; do not erase DK firmware or claim that software reset solved it. Only after a current-candidate `WAITING → RELEASED` read should `--action transport-loss` be retried.

## Same-host RN engine reload / two-generation RF gate (2026-09-27)

The unchanged source runner [`run_dk_pending_read_reload.py`](../../../spikes/archive/nrf-att-hold/run_dk_pending_read_reload.py) completed the **latest candidate** real-iPhone pending-ATT read gate with the validated diagnostic HEX SHA-256 `e7a66e9aebd81495fa77b88ccb15702df3dd0424cf2c192b02a4d68d5a906304` and J-Link serial `001050252028`; it validates image/target identity without flashing the DK. Primary ignored evidence: `.work/nrf-att-hold-dk/rn-pending-read-reload-d8792205409b406cb2bca82fa94bc917.attempt.log` (RN markers) and companion `.runner.log`. The firmware/control result reported for this run was old hold sequence `21` reaching `EXPIRED` with an old GAP disconnect, followed by new sequence `22` reaching `RELEASED`; these firmware states are not printed in the cited RN attempt log. The earlier `.work/nrf-att-hold-dk/rn-pending-read-reload-34455fd4a5784a1ba5361751b6264237.attempt.log` remains an **earlier candidate's JS-boundary-only pass** (sequences `19`/`20`), not the primary evidence for native cleanup.

The two generations are probe/runtime instances on either side of one RN engine reload, not two BleHub plugin versions. In the new log, the old native `read-accepted` marker with exact `runId=d8792205-409b-406c-b2bc-a82fa94bc917` and `probeId=34b60b5a-e045-490b-b309-74a75e7e0a79` records command `12008`, connection `12004`, GATT session `12006`, characteristic `13` **before** the old JS `read-dispatched`. The read was held when the host posted the `RCTTriggerReloadCommandListeners` reload notification. After `generation=1:cleanup-started`, the *same run/probe/IDs* emitted `native:dispose-returned` then `native:late-submit-rejected`, both before generation 2's `arm-ready`. The first marker is an independent observation that `BleHub.dispose()` returned; the second records rejection by the closed `NitroTestSink` of a **synthetic** `.characteristicRead` submitted directly by the private test-only [`HybridBleHubProbe.swift`](../../../integrations/react-native-internal/ios/HybridBleHubProbe.swift). Its `NotificationCenter` diagnostic is not a CoreBluetooth callback. These markers do not establish that an actual native late callback occurred or that events already submitted to Nitro's JS queue drained.

After the old GAP disconnect and explicit advertising restart, generation 2 initialized, scanned, connected and rediscovered using command `13008`, connection `13004`, GATT session `13006`, characteristic `13`. The native `arm-notification-received` barrier and JS `Linking` event both passed (`arm-linking-dispatched:accepted=true`, then `arm-js-observed:source=linking:url=matched`); the new read after `RELEASED` returned `value=00`. The ordered two-generation ledger passed with no old-ID leakage **in the observed JS/event stream**. This proves a bounded RF recovery plus the separate native dispose-return/closed-sink rejection boundaries, not universal native late-callback quarantine, full `rf-io`, physical USB-fault recovery, or a maintained provider. For this candidate the signed Xcode iPhone device build passed (reported separately from the RF attempt log), and `pixi run python -m unittest discover -s ../blehub/spikes/archive/nrf-att-hold -p 'test_*.py' -q` from `nrftest` passed **57 hardware-free tests**. The RF attempt itself did not run a package/single-image gate. In the subsequent non-RF follow-up, `pixi run python tools/react_native/check_single_image.py ios tests/consumers/react-native-internal/ios/build/device-derived/Build/Products/Debug-iphoneos/BleHubNitroHost.app/BleHubNitroHost.debug.dylib` passed on the signed device build product. This is the host dylib UniFFI symbol checker, not an independent staged-package/clean-consumer gate.

Earlier attempts failed this gate because of a one-second-over-strict time limit, missing restart advertising after the first GAP disconnect, and an RN Settings cache that was not live; none is counted as a pass. A separate non-RF reload-signal check passed with a `0.153 s` response; that timing is not an RF result.

## Outstanding before promotion

- The existing `rf-io` event stream fails closed on the first error, so these markers prove an observed command `9010` failure, **not** exactly-once error delivery, absence of late callbacks, full teardown, listener/probe close, or post-disconnect silence.
- The latest same-host RN engine reload passed the observed JS/event ledger and fresh-generation RF recovery, plus native dispose-return and test-only synthetic closed-sink rejection for the old probe. Actual CoreBluetooth late callbacks, callbacks already handed to Nitro, and native callback quarantine remain unverified.
