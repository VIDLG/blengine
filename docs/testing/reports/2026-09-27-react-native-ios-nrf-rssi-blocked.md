# React Native iPhone connected RSSI: build passed, RF launch blocked

Date: 2026-09-27. Scope: the private RN/Nitro integration and standalone nRF52840. **This is not a connected RSSI RF pass.**

The existing production Rust `ReadRssiCommand` / `RssiRead` contract and Apple CoreBluetooth callback were exposed through the private Nitro probe using `readRfRssi(commandId, connectionId)` and an optional numeric `rssi` on the existing RF event projection. The standalone gate uses provider-filtered scan, connect, an ID-correlated native `rssiRead` before the successful command terminal, requested disconnect, one-second post-disconnect silence and close. No RSSI value is synthesized by the fixture or the deterministic Android probe. See the [Nitro spec](../../../integrations/react-native-internal/specs/BleHubProbe.nitro.ts), [Swift adapter](../../../integrations/react-native-internal/ios/HybridBleHubProbe.swift), [JS scenario](../../../tests/consumers/react-native-internal/src/App.tsx), and [independent checker](../../../tools/react_native/check_runtime_log.py).

`pixi run just react-native host-ios-device-build 00008110-000C61160C39401E FWVYQ287W5` succeeded, and the resulting device app passed the iOS single-image check. Android `host-android-build` and the Android APK single-image check also passed after updating two deterministic-probe overrides to the currently generated Nitro enum signatures; this is static integration, not Android BLE/RF evidence.

The first `pixi run just react-native host-ios-device-rf-rssi 00008110-000C61160C39401E FWVYQ287W5` attempt built and installed the host and started the fixture, but `devicectl --console` failed **before application launch** with `BSErrorCodeDescription = Locked`. There was no RN JS/RSSI callback evidence to check. The runner stopped its owned fixture; provider status was `nrf52840_fixture=stopped`, the RN lock and RSSI coordination directory were absent, and no matching detached fixture or device-console process remained. At the time of this blocked attempt the ignored `device-rf-rssi.attempt.log` contained the CoreDevice error; the later successful recipe cleared that transient attempt log before writing its verified `device-rf-rssi.log`. The blocked attempt did not overwrite a verified RF result.

The subsequent [unlocked-device full-recipe rerun](2026-09-27-react-native-ios-nrf-rssi.md) passed independently, so this report remains historical evidence of a launch-blocked attempt, not the current gate status. An Int16-range value is evidence of the native CoreBluetooth reading only; it is not an RF calibration or signal-quality guarantee.
