## Remaining architecture boundaries

- [`HybridBleHubProbe.kt`](../../integrations/react-native-internal/android/src/main/java/com/margelo/nitro/blehubreactnative/HybridBleHubProbe.kt) still calls synchronous `BleHub.dispose()` and wrapper `close()` on the Nitro caller and creates a fresh Promise on every `close()`. Swift instead retires listener routes and runs dispose off the caller stack while sharing the close Promise. Android static compilation does not validate the eventual real-backend close latency; before Android runtime admission, move cleanup off the caller, share a single completion and test duplicate close/error/late callback behavior.
- Both hosts had basic probe paths that returned early without closing. These now remove the listener and explicitly close in `finally`; static TypeScript checks passed, but interrupted device/macOS UI builds were not rerun. The archived macOS workflow shared similar command/bytes/listener assertions with the mobile host; no shared helper is needed solely to maintain an archived desktop lane. Do not export test helpers as a second production BLE API.
- Swift's `BoundedEventHandoff` bounds only its native-to-probe hop, not Nitro's generated JS callback queue. Queue overflow, pending Promise cleanup and full command/event API are not yet formally admitted. Device RN BLE RF and public `BLeng` remain unrun/unimplemented.
- Do not add NativeWind/Gluestack to solve a black screen: styling packages cannot prove bundle loading or native view presentation. The internal hosts currently need only RN-native `View`, `Text` and `ScrollView`. Any future product component kit should first be evaluated on both independently pinned RN versions and macOS support, with explicit artifact/lifecycle checks.
