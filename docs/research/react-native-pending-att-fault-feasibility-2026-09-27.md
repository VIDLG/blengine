# RN iPhone pending ATT fault/reload gate: fixture feasibility

Date: 2026-09-27. Status: source audit, **not RF evidence or an approved firmware change**. Scope: the current private RN/Nitro iPhone host, standalone nRF52840 BTP Peripheral and production Apple backend.

## What is already covered

The RN host has a real active-Notification engine-reload gate and a separate real characteristic I/O RF gate, but neither asserts that a native ATT read/write request was still in flight at the fault boundary. See the [active-reload report](../testing/reports/2026-09-27-react-native-ios-nrf-active-reload.md) and [I/O report](../testing/reports/2026-09-26-react-native-ios-nrf-gatt-io.md). The Apple controller's deterministic `testRetireFailsAllAcceptedCommandsAndQuarantinesLateCallbackRoute` already exercises accepted read and queued write retirement, failure terminals and quarantine of a late read callback in [`GattIoControllerTests.swift`](../../platforms/apple/Tests/BleHubAppleTests/GattIoControllerTests.swift). `pixi run -e apple-ci just apple test` passed this candidate (Apple backend macOS Swift tests and 16 RF-selection XCTest tests); this is **not** a new iPhone pending-ATT RF pass.

## Why the current fixture cannot prove the proposed boundary

- The upstream Zephyr Tester [`read_value()`](../../../contrib/zephyr/tests/bluetooth/tester/src/btp_gatt.c) reads the attribute and returns directly. There is no server-side read-entered event or hold control. The [`BTP GATT event definition`](../../../contrib/zephyr/tests/bluetooth/tester/src/btp/btp_gatt.h) exposes `ATTR_VALUE_CHANGED`, not an ATT request-entered event.
- The Tester [`write_value()`](../../../contrib/zephyr/tests/bluetooth/tester/src/btp_gatt.c) updates the value and emits `ATTR_VALUE_CHANGED` immediately before returning. Zephyr's [`att_write_req()`](../../../contrib/zephyr/subsys/bluetooth/host/att.c) sends the Write Response after `perform_write()` returns. Thus the value-changed event verifies a write to the attribute, **not** a held callback or that the ATT response remained outstanding when the host saw the event.
- The external golden reference [`wait_for_write()`](../../../nrftest/host/nrftest/fixture.py) observes that value-changed event; the current BleHub [`DirectFixture`](../../tests/peripherals/nrf52840/direct_fixture.py) only coordinates subscription/value, normal GAP disconnect, recovery and host-close. Its GAP fault is synchronized with a connected/subscribed state, not an ATT callback-entry barrier.
- The BleHub [`BtpSession`](../../tests/peripherals/nrf52840/btp_session.py) has one serial request owner and polls events only while no request is pending. A callback held inside firmware would need a verified independent way to release or abort; simply putting `sleep()` in a Python runner, looking for JS dispatch acceptance, or treating the value-changed event as entry would not create that guarantee.
- The golden reference's `TRIGGER_PENDING` marker in [`btp_gatt_passive_disconnect_fixture.py`](../../../nrftest/tools/btp_gatt_passive_disconnect_fixture.py) denotes a timer before GAP disconnect after connection/optional CCC verification. It is **not** an ATT operation pending marker.

These are source-verified limits of the current fixture. Whether a separate tester command thread can service a new release request while an ATT callback is blocked is **inferred as possible, not validated on hardware**. Callback scheduling, transport delivery, disconnect while held, and bounded recovery need an isolated experiment.

## Proposed gate, subject to review

A genuinely synchronized pending-ATT RF test needs a **test-owned, opt-in diagnostic firmware/control variant**, not changes to the production BLE contract, the default nRF profile or a silently modified vendored Zephyr tree. This extends the approved nRF provider ownership direction in [`.plan/PLAN.md`](../../.plan/PLAN.md), so the concrete firmware/control protocol should be reviewed in the plan before implementation.

1. First prototype one readable attribute with a callback-entry event carrying generation/connection/handle/operation, a bounded hold and an explicit release/abort mechanism; guarantee timeout cleanup and ensure the control path really runs while the callback is held. Avoid indefinite firmware waits. Build the variant reproducibly under `tests/peripherals/nrf52840`, independent of `nrftest` as a runtime dependency.
2. Prove entry → hold → release → ATT result without fault on physical hardware before attempting reload/fault. An entry marker alone is insufficient; the firmware must confirm that the callback has not returned at the fault boundary.
3. Only then, while held, trigger either RN engine reload or a controlled Peripheral fault; correlate old command ID, terminal outcome/route teardown, fresh-generation recovery, and lack of late delivery through the independent checker. A host app close may legitimately prevent the old JS Promise from resolving; it must not be used as proof of completion.
4. Require bounded fixture stop/reset, hardware identity and session ownership checks, and explicit verification that a failed diagnostic leaves the standard RF profile usable. A test-owned firmware change must not become a production or default-build dependency.

An additional repeat active-Notification reload soak can be built with the existing provider, but it tests a **different** boundary and cannot close this pending-ATT gap. An isolated test-only [read-hold firmware/host-protocol spike](../../spikes/archive/nrf-att-hold/README.md) now explores the control-thread boundary without changing the maintained provider or applying a patch to the shared Zephyr checkout. On 2026-09-27 its separate diagnostic HEX built successfully with the opt-in Kconfig and application flash bounds validated; a distinct DFU ZIP was normalized and parsed by the pinned Nordic tool. The standard firmware ZIP remained intact. The diagnostic firmware was **not flashed**, and neither BTP control-thread feasibility on hardware nor pending-ATT RN RF was tested. This does not close the pending-ATT RF gap or approve a firmware architecture change.
