# React Native BLE implementations versus BleHub/BLeng — 2026-09-26

Status: local-source research and design input, **not** a change to the approved plan or a dependency decision. No build, device runtime, RF test, benchmark, or dependency-source audit was run for these three libraries.

The comparison baseline is the [approved plan §5.6–5.6.1](../../../.plan/PLAN.md): `BleHub` owns the canonical synchronous dispatch-acceptance/command-event contract; platform backends own native handles and unavoidable GATT callback correlation; future optional `BLeng` owns Rust-side async operation waiters, timeout/cancellation, retry and application state; the React Native Nitro adapter maps types, lifecycle and delivery without becoming a second BLE engine. `BLeng` is **not implemented or admitted as a public RN API**. The current [`BleHubProbe` spec](../../../integrations/react-native-internal/specs/BleHubProbe.nitro.ts) is private, low-level evidence, not the proposed public interface; see the [integration-boundary review](react-native-integration-boundary.md).

These are three complete BLE libraries in their own right, not three alternative transports for an existing BleHub runtime. A JavaScript Promise resolving on BleHub dispatch means **accepted for dispatch**, whereas a future BLeng operation Promise must wait for its defined domain/terminal result. Neither Promise alone proves physical cancellation or remote receipt.

## Implementation findings

### `react-native-ble-plx`: application-facing object API, external native engines

- [`BleManager.js:53–113,119–169`](../../../../contrib/react-native-ble-plx/src/BleManager.js) implements a shared JS manager, creates the native client at construction, tracks active Promises/subscriptions, and retires them around `destroy()`. Device/service/characteristic wrappers retain the manager, e.g. [`Service.js:54–77`](../../../../contrib/react-native-ble-plx/src/Service.js). Operation Promises and monitoring callbacks are designed for app consumption, not for the BleHub command/event boundary.
- Android's [`BleModule.java:65–82,1318–1439`](../../../../contrib/react-native-ble-plx/android/src/main/java/com/bleplx/adapter/BleModule.java) holds connection/discovery/transaction state and delegates BLE operations to RxAndroidBle, pinned by [`android/build.gradle:87–94`](../../../../contrib/react-native-ble-plx/android/build.gradle). iOS [`BlePlx.m:57–69,161–196`](../../../../contrib/react-native-ble-plx/ios/BlePlx.m) forwards into the separate `MultiplatformBleAdapter` pod declared in [`react-native-ble-plx.podspec:17–19`](../../../../contrib/react-native-ble-plx/react-native-ble-plx.podspec). **The actual native iOS engine and RxAndroidBle's internal GATT serialization are outside this audit.** Do not infer their ordering or cleanup guarantees from this wrapper.
- Android constructs service/characteristic identifiers using native instance information (see [`IdGeneratorKey.java`](../../../../contrib/react-native-ble-plx/android/src/main/java/com/bleplx/adapter/utils/IdGeneratorKey.java) and [`Characteristic.java:35–40`](../../../../contrib/react-native-ble-plx/android/src/main/java/com/bleplx/adapter/Characteristic.java)); it is **not** purely UUID-only. However, UUID-based convenience lookup can choose the first matching instance ([`Device.java:83–94`](../../../../contrib/react-native-ble-plx/android/src/main/java/com/bleplx/adapter/Device.java)). The JS [`index.d.ts:7–32`](../../../../contrib/react-native-ble-plx/src/index.d.ts) uses numeric object identifiers, string transaction IDs and Base64 values; this does not establish a lossless mapping for BleHub `u64` IDs.
- [`BleModule.java:1042–1045,1452–1489`](../../../../contrib/react-native-ble-plx/android/src/main/java/com/bleplx/adapter/BleModule.java) shows transaction cancellation by disposing an Rx subscription and notification delivery using `BackpressureStrategy.BUFFER`; this is not evidence of over-the-air rollback or a bounded JS-facing queue. Scan restart deserves explicit testing: JS replaces its tracked listener ([`BleManager.js:369–396`](../../../../contrib/react-native-ble-plx/src/BleManager.js)), and Android replaces a stored scan subscription on start ([`BleModule.java:1175–1206`](../../../../contrib/react-native-ble-plx/android/src/main/java/com/bleplx/adapter/BleModule.java)); this code alone does not establish single-scan enforcement.
- Packaging uses RN native bridge/event-emitter entry points, not Nitro/UniFFI; see [`src/BleModule.js`](../../../../contrib/react-native-ble-plx/src/BleModule.js) and [`ios/BlePlx.m`](../../../../contrib/react-native-ble-plx/ios/BlePlx.m). The [`BleManager` Jest tests](../../../../contrib/react-native-ble-plx/__tests__/BleManager.js) mock the native module; they do not prove real RF or the uninspected native dependency's behavior.

**Reference:** high-level manager/device API, operation result versus persistent event, explicit destroy, transaction IDs, and instance-ID-aware navigation. **Do not copy:** eagerly creating a BLE client merely by constructing a public JS wrapper, unbounded notification-buffer assumptions, Base64 as a mandated wire representation, or RN-only ownership in place of a reusable Rust BLeng layer.

### `react-native-ble-manager`: RN-facing facade over platform-owned state machines

- [`src/index.ts:30–43,282–299,523–583,944–1017`](../../../../contrib/react-native-ble-manager/src/index.ts) chooses a Codegen TurboModule or legacy native path, wraps callback operations in Promises, and separately exposes event subscriptions. It is **not** Nitro and does not correlate operations through BleHub's caller-supplied `command_id` and terminal/domain events.
- iOS [`SwiftBleManager.swift:8–33,117–194`](../../../../contrib/react-native-ble-manager/ios/SwiftBleManager.swift) owns a `CBCentralManager`, peripheral map, callback dictionaries, timers and write queues. Android [`Peripheral.java:59–98,958–1003`](../../../../contrib/react-native-ble-manager/android/src/main/java/it/innove/Peripheral.java) owns per-device GATT, callbacks and a main-thread command queue. These are platform-backend patterns to compare, **not** state that belongs inside BleHub's RN adapter. The examined Android queue is not a documented bounded RN event transport.
- Android [`DefaultScanManager.java:195–335`](../../../../contrib/react-native-ble-manager/android/src/main/java/it/innove/DefaultScanManager.java) uses a scan generation/session ID so an earlier timeout cannot stop a newer scan. iOS notification state callbacks and Android CCCD descriptor-write callbacks complete subscription changes (see [`SwiftBleManager.swift:1069–1148,1796–1874`](../../../../contrib/react-native-ble-manager/ios/SwiftBleManager.swift) and [`Peripheral.java:592–629,695–765`](../../../../contrib/react-native-ble-manager/android/src/main/java/it/innove/Peripheral.java)). They provide concrete local-versus-callback-completion questions for BLeng tests.
- Service/characteristic enumeration preserves UUID data, but public UUID-path selection cannot unambiguously identify repeated UUID instances; iOS helper lookup takes a first match ([`Helper.swift:187–274`](../../../../contrib/react-native-ble-manager/ios/Helper.swift)), and Android includes a property-based tie-breaker before UUID fallback ([`Peripheral.java:797–829`](../../../../contrib/react-native-ble-manager/android/src/main/java/it/innove/Peripheral.java)). BleHub's GATT instance IDs must not be replaced by such a convenience path.
- Two verified rejection-path hazards are useful test cases: Android [`BleManager.java:318–343`](../../../../contrib/react-native-ble-manager/android/src/main/java/it/innove/BleManager.java) returns from one Bluetooth-off scan path without completing its callback; iOS [`SwiftBleManager.swift:551–588`](../../../../contrib/react-native-ble-manager/ios/SwiftBleManager.swift) stores a discovery callback before checking service UUID validity and returns an error without retiring the stored route. They can leave pending or stale callback state; this is a source-level observation, **not** a claim about measured production incidence. iOS reload and Android `invalidate()` have different teardown paths ([`SwiftBleManager.swift:71–101`](../../../../contrib/react-native-ble-manager/ios/SwiftBleManager.swift), [`BleManager.java:1060–1080`](../../../../contrib/react-native-ble-manager/android/src/main/java/it/innove/BleManager.java)).
- Its [`RNBleManager.podspec`](../../../../contrib/react-native-ble-manager/RNBleManager.podspec) and [`package.json`](../../../../contrib/react-native-ble-manager/package.json) integrate native source and RN Codegen, not one BleHub UniFFI image. Located [`example/__tests__/App-test.tsx`](../../../../contrib/react-native-ble-manager/example/__tests__/App-test.tsx) is a render smoke, not evidence of lifecycle or RF behavior.

**Reference:** native callback ordering, scan-generation isolation, CCCD enable/disable results, and error/cleanup regression cases. **Do not copy:** TurboModule/legacy glue as a Nitro architecture, UUID-only addressing, callback registration before validation, or an unbounded queue as the RN event-handoff policy.

### `react-native-ble-nitro`: relevant Nitro packaging, separate BLE implementation

- [`nitro.json`](../../../../contrib/react-native-ble-nitro/nitro.json) registers factory/manager HybridObjects; [`NativeBleNitro.nitro.ts:88–129`](../../../../contrib/react-native-ble-nitro/src/specs/NativeBleNitro.nitro.ts) defines scan, connect, GATT, RSSI and notification callbacks directly across Nitro. [`src/manager.ts:332–358,577–603,612–763`](../../../../contrib/react-native-ble-nitro/src/manager.ts) composes some callbacks into app-facing Promises, including a JS-side discovery timeout; a timer expiring does not cancel native discovery.
- The Swift implementation owns CoreBluetooth ([`BleNitroBleManager.swift:34–59`](../../../../contrib/react-native-ble-nitro/ios/BleNitroBleManager.swift)); Kotlin owns `BluetoothGatt` instances ([`BleNitroBleManager.kt`](../../../../contrib/react-native-ble-nitro/android/src/main/java/com/margelo/nitro/co/zyke/ble/BleNitroBleManager.kt)). Its Kotlin GATT queue at `BleNitroBleManager.kt:65–103,494–539` covers descriptor writes; reads/writes and discovery have separate submission paths (`:832–996`). It does **not** demonstrate a general per-connection read/write/subscription FIFO.
- Swift [`BlePeripheralDelegate.swift:32–42,114–169`](../../../../contrib/react-native-ble-nitro/ios/BlePeripheralDelegate.swift) indexes callbacks by characteristic UUID rather than exact native object and operation generation; concurrent or overlapping value routes therefore warrant explicit verification. Both public spec and native lookup use UUID paths, and Swift selects the first matching service/characteristic ([`BleNitroBleManager.swift:379–395,555–569`](../../../../contrib/react-native-ble-nitro/ios/BleNitroBleManager.swift)); this is not a substitute for BleHub's duplicate-UUID instance IDs.
- [`BleNitroBleManager.swift:450–470`](../../../../contrib/react-native-ble-nitro/ios/BleNitroBleManager.swift) and Kotlin `BleNitroBleManager.kt:974–991` complete no-response writes at local submission; neither proves Peripheral receipt. Kotlin [`CccdSubscription.kt:20–38`](../../../../contrib/react-native-ble-nitro/android/src/main/java/com/margelo/nitro/co/zyke/ble/CccdSubscription.kt) chooses notification over indication when both are available; its [`CccdSubscriptionTest.kt`](../../../../contrib/react-native-ble-nitro/android/src/test/java/com/margelo/nitro/co/zyke/ble/CccdSubscriptionTest.kt) verifies the choice. The spec has no BleHub-style strict-indication request. Kotlin may report a successful subscription when CCCD is absent (`BleNitroBleManager.kt:1042–1067`); a caller must not infer native subscription confirmation without a callback contract.
- Swift [`BlePeripheralDelegate.swift:262–283`](../../../../contrib/react-native-ble-nitro/ios/BlePeripheralDelegate.swift) has callback cleanup, but the examined disconnect path removes the delegate without invoking that helper ([`BleNitroBleManager.swift:698–722`](../../../../contrib/react-native-ble-nitro/ios/BleNitroBleManager.swift)); an unresolved pending operation is a **risk inferred from that route**, not a reproduced failure. Android drains pending discovery on disconnect, but the examined disconnect/close path does not visibly retire all separate read/write/descriptor routes (`BleNitroBleManager.kt:308–437`). No explicit manager `close()`/RN invalidation path was found in the examined spec and implementations; full reload safety remains unverified.
- [`BleNitro.podspec`](../../../../contrib/react-native-ble-nitro/BleNitro.podspec) and [`android/CMakeLists.txt`](../../../../contrib/react-native-ble-nitro/android/CMakeLists.txt) show Nitro source/codegen packaging. No `Package.swift` was found in this checkout. The available [`Jest suite`](../../../../contrib/react-native-ble-nitro/src/__tests__/index.test.ts) mocks the native object, while the CCCD-selection test is a narrow JVM test; neither proves device RF, callback ordering under load, single UniFFI image, or RN reload/close.

**Reference:** Nitro HybridObject/factory shape, `ArrayBuffer` mapping candidates, generated glue/podspec structure, and explicit platform-mode tests. **Do not copy:** its independent Swift/Kotlin BLE engines, UUID-keyed callback association, descriptor-only queue as complete GATT serialization, or a name/README performance claim as benchmark evidence.

## Trade-offs against BleHub/BLeng

| Criterion | Self-contained RN BLE libraries: benefits and costs | BleHub + future BLeng + thin Nitro: benefits and costs |
|---|---|---|
| Time to a usable RN UI API | Existing scan/connect/read/write/notify APIs and demos; less initial implementation for an RN-only app. Library-specific BLE behavior, identifiers and lifecycle become the application's contract. | Higher up-front Rust facade, FFI, codegen and package effort; the public BLeng API is **not shipped yet**, so no present ease-of-use advantage can be claimed. |
| Reuse beyond RN | Swift/Kotlin/iOS/Android native engines can be effective for RN but are tied to their own package architecture; PLX additionally depends on external BLE adapters. | The same BleHub contract/platform backends and planned BLeng semantics can serve Rust and foreign consumers across approved platforms without duplicating operation policy in each RN adapter. This is a design advantage, not yet a validated public BLeng runtime. |
| Callback and GATT identity | Convenience UUID paths are concise; some, notably PLX Android, also expose native-instance-derived IDs. Other paths can select the first match or key callbacks by UUID. | Canonical command/connection/GATT-instance IDs and backend correlation preserve duplicate UUID instances and late-event safety; the cost is more IDs and explicit mapping across Rust/UniFFI/Nitro. Do not add a UUID shortcut that silently discards ambiguity. |
| Async, cancellation and native completion | Direct Promises simplify application use, but return semantics differ by operation; JS timeout/cancel is not necessarily native cancellation. | BLeng can unify operation waiter, timeout, cancellation and passive-disconnect policy around `command_id` and domain/terminal events. The core deliberately does **not** own those resources; implementing and testing this actor remains work. |
| Transport, performance and packaging | Nitro provides a typed JSI path; PLX/Manager use different RN bridge/Codegen paths. None of these checkouts proves a cross-library throughput ranking or BleHub-like single-image packaging. | Extra UniFFI/native→Nitro crossings and event handoff can cost latency/CPU and complicate build/signing; exact overhead and backpressure must be measured, not assumed away. Current Nitro iOS SwiftPM replacement remains blocked by mixed-language packaging; CocoaPods is the maintained path (see [SwiftPM spike](react-native-ios-swiftpm-spike-2026-09-25.md)). |
| Testability and maturity | Shipped RN APIs provide a practical baseline; examined JS tests mainly mock native behavior and cannot establish RF, teardown or concurrency semantics. | BleHub has backend/conformance and platform-specific evidence, but this does **not** prove BLeng or a released RN high-level consumer. Its own RN gate must cover iOS **and** Android artifact, lifecycle, queue overflow, reload and RF separately. |

A different product goal could justify a different choice: for a **mobile RN-only application** wanting an existing BLE API quickly, integrating a self-contained RN library may be less work. For BleHub's approved **cross-consumer, one-contract, one-production-image** goal, adopting one as the engine would introduce a competing source of BLE state and discard the architecture's main benefit. This is a recommendation conditional on that goal, **not** a claim that the other libraries are generally inferior.

## Actionable design and validation questions

1. Design the future public `BLeng` API with scan sessions, device/connection handles, explicit GATT-instance identity, typed errors, subscription removal and deterministic close. Compare its ergonomics with PLX/Manager without committing to their exact object models or representations.
2. Test waiter registration before dispatch, synchronous rejection, terminal-before-domain ordering, domain errors, timeout without assuming native cancellation, duplicate/late callbacks, passive disconnect and close/reload while an operation is pending. The BLE Manager failure paths above are particularly useful regression inputs.
3. Test scan restart generation isolation; overlapping GATT operations, duplicate-UUID instances, read-versus-notification value routing, no-response local-submission semantics, CCCD callback confirmation, and strict notification/indication mode selection.
4. For the RN bridge, test lossless `u64` projection, byte transport, bounded handoff and overflow policy, single production image, listener removal without starving BLeng waiters, explicit disposal, artifact-only host consumption, and actual iOS/Android device RF. Do not reclassify a mocked JS test, a backend RF pass, or a Nitro demo as these gates.
5. If further architectural borrowing depends on RxAndroidBle's or MultiplatformBleAdapter's queue/cancellation behavior, obtain their pinned source revisions in the workspace first; this report did **not** audit those transitive implementations.

No source, dependency or approved-plan change is proposed by this report.
