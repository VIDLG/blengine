Read this file before researching, planning or changing BleHub. Keep it as current working rules and a short navigation guide, not an accumulating execution log.

When sources disagree, use this order:

1. Explicit instructions in the current user conversation.
2. This `AGENTS.md`.

Research and test reports do not silently change the approved plan. Make proposed architecture changes explicit for user review. Updating this file does not declare a phase complete or freeze an ABI.

## Production Architecture Guardrails

- `crates/blehub` owns the canonical `BleHub`, unified commands/DTOs/events/errors, foreign `BleBackend`, foreign `BleEventSink` and direct ingress.
- Each maintained package line has one final Stable UniFFI image: thin `crates/blehub-uniffi` owns the BleHub-only image; `crates/bleng-uniffi` owns the BLeng image combining the canonical `blehub` + `bleng` components. They own bindgen/package staging, not duplicate APIs. A host consumes one line, never both images or a second test native image; see Plan §5.6.1.
- `BleBackend` and `BleEventSink` have ordinary non-async methods. Commands are fire-and-forget: synchronous `Result` means dispatch accepted/rejected; eventual native/BLE outcomes are events. BLeng's `begin_*` is a different boundary: synchronous, timeout-free bounded submission returning a typed handle or submission error; actor admission and backend/BLE outcomes arrive through async `wait`, with independent async `cancel`. Convenience methods share this same submission/result mechanism. No legacy async begin path; see Plan §16.1.9.
- BleHub core owns no runtime, executor, worker, mailbox, timer, event loop or canonical BLE device/GATT state. Caller command IDs, application timeouts/cancellation policy, stale/duplicate handling and business state remain outside the thin core. The separate `crates/bleng` layer and private RN probe must not be confused with the core's responsibilities.
- Backends own native handles, callback correlation, serialized bounded native I/O lanes and native safety watchdogs. Existing watchdog/cancellation/retirement semantics must not be weakened to make a test pass. Native submission is not remote delivery, platform cancellation is not remote rollback, and process death does not prove old Probe close/resource-zero.
- Backends retain `BackendEventIngressHandle`; Rust holds only a weak reference to per-Hub ingress. No token/process-local routing registry. Downstream sinks choose their delivery mechanism.
- Production backends live under `platforms/`; reusable Rust test support is `tests/support/blehub-testkit`; direct Swift/Kotlin production ABI probes are in `tests/ffi/runtime`; staged artifact-only consumers are under `tests/consumers`. Production/long-lived test paths must not depend on `spikes/` or `archive/` implementations.
- Apple uses system CoreBluetooth directly, not high-level reactive/async BLE wrappers. The audited Nordic mock is not part of production/test targets; see [Swift ecosystem assessment](docs/research/platform/swift-ble-ecosystem-assessment.md).
- Linux/BlueZ remains a separately reviewed later phase. Archived Windows wire/error shapes are not removed merely because the platform is archived.

## Tooling And Cleanup Discipline

- Rust dependencies use Cargo; external development tools use Pixi; recipes are in `justfile` and imported `just/` modules. Run `pixi run just <recipe>`, not assumed global Python/Just/Ruff/RTK/sccache.
- Reuse by responsibility: thin CLI → named runner → bounded capture/platform control → scenario ledger → evidence bundle. Shared mechanics must not own scenario facts. Live runners/providers must not import synthetic support or TestCase modules. Native BLeng iOS system-loss uses `tools/apple/system_loss_host.py` as the one-shot host protocol owner: it validates provider readiness, one OFF, one ON restoration, old-operation terminals and same-owner new identities; a live XCUITest/radio adapter is injected separately and must not be replaced by the RN startup-off schema.
- Fault firmware exports bounded capture/resolve/receipt/retirement mechanisms, not RN scenarios, retry plans or platform verdicts. Keep family admission and scenario policy above generic encoders/builders; preserve firmware-enforced lifetime, resource and deadline safety. Change code in its owning repository; when commits are authorized, commit there and pin reviewed revisions. Do not duplicate a codec or add a framework merely for anticipated reuse.
- Tool tests belong to `tools/tests/react_native/`; owner-local synthetic data to its `support/`; cross-layer pure samples to `tests/support/rf_lab/`; Peripheral emulators to `tests/peripherals/nrf52840/support/`. The live provider remains real infrastructure despite its `tests/` location.
- Before adding a tool/helper/entry, check existing owners and recipes. Do not create a generic registry/driver/cleanup framework merely for directory symmetry. A single App does not require a universal runner.
- Delete unused implementation only after checking imports, CLI/Just references, test discovery and documented/manual use. Standalone diagnostic gates are not dead merely because full-suite overlaps them. Archive/history is not active code; preserve original reports, failed attempts and unique safety regressions. Do not delete live diagnostic dependencies with a retired entry.
- Maintain a small set of discoverable Just entry points. Add necessary controller tests to canonical discovery rather than relying on one-off manual test commands. RN `host-test` is the maintained Jest discovery; named scripts are targeted subsets. `tools-test` is included in `tools-fixture-test`; do not require both. Prefer targeted/incremental daily checks, explicit clean candidate builds and separately authorized device gates. Test/file count is not a coverage or cleanup target. Synthetic tests must mock the actual device-facing SDK/install boundary; placeholder identities must never reach real device commands. Do not replace isolation with a global always-success mock.
- Save full build/device output to ignored logs; use bounded deadlines and progress summaries. After timeout inspect the log and clean only attempt-owned processes before deciding on a retry; do not blindly extend silent waits. Short tool probes also need deadlines and must not wait on inherited background-process pipes. RTK must preserve exit status/failure detail; sccache wraps eligible Rust/C/C++, not Swift/Kotlin. Generate bindings with the locked UniFFI and same candidate library.
- Artifact-only consumers must resolve native/generated headers and libraries from installed artifacts, never checkout-relative includes or search paths. Preserve leakage, archive provenance and single-image checks; do not rewrite away a missing package dependency merely to pass.

### Machine Setup And Safety

Except Apple Swift/Xcode, tool roots resolve through `BLEHUB_<TOOL>_ROOT` and ignored `blehub.local.toml`; Android then honors `ANDROID_HOME`/`ANDROID_SDK_ROOT` and the shared platform-standard SDK location. Other managed tools default to `~/.cache/blehub/toolchains/<tool>`. Inspect with `pixi run just toolchain-paths`; keep paths/endpoints local and versions/URLs/hashes/license policy tracked.

Apple Swift comes only from the selected Xcode on the real Mac mini. No `BLEHUB_SWIFT_ROOT`, local `swift_root` or project Swift bootstrap. Tool installs, SDK/NDK replacement and license acceptance must be explicit, never hidden in ordinary build/test. XcodeGen installation uses the explicit Apple install-tools recipe.

Never request/collect a password in the agent terminal or configuration. Keychain unlock, signing approval, `sudo` and developer authorization are explicit human-only setup. Use the documented Apple unlock recipe when needed; ordinary tests must not request passwords. Physical iOS UI uses XCUITest; keep its no-terminal-input settings and do not bypass authentication or relabel runner initialization failure as test execution.

Apple doctor is read-only and mode-scoped (`build-signing` / `prebuilt`), without implicit package builds or project generation. Device readiness, visible signing identity, private-key access, TCC, UI automation and RF are separate observations, not a cached permission grant. Ordinary prebuilt native RF does not require XCUITest. Only explicit `success_app=close-owned` may close this run's identity-verified iOS App between scenes; the default keeps the successful page and unknown old Apps remain refused. See [Apple preflight](docs/testing/apple.md#scoped-read-only-preflight).

- The one available Android test phone is already rooted. Reuse the existing root-aware installer for explicitly authorized provisioning; root use or OEM installer confirmation is not itself an architecture blocker. Ordinary runs still do not silently provision helpers, change DUT BLE permissions/radio, or adopt unknown automation owners. Evaluate Appium helper/settings behavior by scope and restoration, not a blanket no-root/no-mutation rule.
- An absolute Android SDK `adb` path pins the client, not the shared host daemon's executable/version/ownership. For transport failures inspect the actual listener/process provenance before attribution; ordinary runs must not kill/restart a foreign daemon or close another App's ADB/mirroring clients. Such shared-host setup changes need explicit authorization and can interrupt other connections; version drift alone is not a proven failure cause.
- RF uses **provision changes / assert proves / run tests**. Ordinary run never flashes/resets firmware or auto-retries destructive gates. Require explicit device identity, contract/profile and live installed-image receipt under the physical lease before App execution. Android permission revoke can kill the entire UID: PID loss alone is not cause-of-death proof. Restore permissions before phone-lease release and preserve primary errors separately from cleanup failures. Leave successful result pages visible unless explicitly requested otherwise.

## Git And Change Discipline

- Independent Mac/Windows Git clones share remote/history and `main`; no maintained per-host branches. Inspect the worktree first. Pull `--ff-only` only when clean; if dirty, preserve work and do not stash/reset/clean or force synchronization. For divergent histories, review/merge and validate before an explicitly authorized push; never force-push over another host. See [Git workflow](docs/git-workflow.md).
- Do not commit, push or create branches unless explicitly requested. Do not overwrite user work, generated/vendor code or unrelated fixes. Migration instructions in old reports are history, not startup operations.
- Never restart Mutagen against independent Git worktrees or copy `.git`. The legacy sync helper is only for an explicitly requested temporary non-Git copy. Tool environments, local config and build output stay local; exchanging source does not transfer runtime/package/RF evidence between hosts.
- Make minimal focused changes, fix demonstrated root causes, and update related call sites, docs and tests. Do not broaden planning into implementation without approval.

## Validation And Documentation

- Preserve functional and safety contracts, not accidental historical test details. Platform record/format assertions may change based on actual evidence; retain raw observations and original failures. Never broaden reset scope merely to recreate an old display, or weaken identity/lease, permission, error or cleanup guarantees to pass a test.
- Prefer tests protecting wire/FFI validation, lifecycle/rollback, concurrency linearization, platform mapping and observed regressions. Do not add trivial constructor/getter/derived-trait/direct-delegation tests. Combine related boundaries where useful; do not discard unique failure assertions just to reduce counts.
- Keep Rust tests and test-only helpers in neighboring `tests/` directories where possible. Leave only necessary `#[cfg(test)]` fields, hooks and module declarations in production files; do not widen production visibility or remove unique regressions merely to separate tests.
- Start with targeted checks, then relevant combined tests. Report exact commands actually executed and their results; do not infer current passes from old reports, fake/Jest results, package builds or offline integrity.
- For tooling/docs, at minimum run `pixi run just fmt` and `pixi run just lint`. For RN/provider work also use the applicable `react-native tools-test` / `tools-fixture-test`, host typecheck and RN tests. Native changes require affected build/runtime/package gates according to the plan.
- Authored Markdown must decode as UTF-8, have balanced fences, no trailing whitespace or conflict markers, and pass `pixi run just docs-check-mermaid` when diagrams are present. Link factual claims to local source/evidence where practical.
- Keep one architecture plan. Reports store candidate-specific facts and failures; architecture docs store durable responsibilities; this file stores current working rules. Do not turn any of them into duplicate chronological logs.
