# RN host tools

This directory contains executable host tooling and its live implementation, not synthetic test fixtures.

- Formal RN UI lifecycle: `run_bleng_ui` shares one Appium button/state scenario across iOS and Android via the existing platform helpers. `formal-host-ui` is opt-in and attaches only to a host-prepared, already-open idle App; it does not build/install/relaunch the App or prove RF/resource-zero. See the [formal consumer contract](../../tests/consumers/react-native-bleng/README.md#shared-appium-lifecycle-e2e) for setup, ownership, failure cleanup and evidence limits.
- Formal Android managed lifecycle: `run_bleng_android_lifecycle` → `bleng_android_lifecycle.run_android_lifecycle`, exposed by `formal-host-android-managed-lifecycle`. The thin CLI consumes an explicit reviewed prebuilt APK/hash, three helper hashes and separate install/helper-settings authorizations; it does not build, grant DUT BLE permissions, toggle radio or run RF. The runner owns freezing, phone acquisition, helper handoff, install/cold launch, one shared UI lifecycle and ordered cleanup, then seals the lifecycle bundle. Success retains Evidence; an old running App is refused, not adopted/restarted. Optional `--close-diagnostics` owns only `log.tag.BleHubBlengClose` under that same phone lease: record original value, DEBUG/readback, original-PID bounded logcat, independent restore/readback and release recheck. It also observes the exact chosen Close element before clicking once: raw PNG/XML, window/bounds and pinned metadata, with per-read guard/HTTP budget, post-capture UI/identity rechecks and no target re-selection. The same explicit diagnostic scope also enables timestamped local Appium debug output and reads only the already-bound UiAutomator2 server PID's `appium:I` logs once before DELETE. The same opt-in now opens a separate fixed-tag live logcat stream after original App binding and before UI Start, bounded by the scenario/300 seconds, 8 MiB and 64 recent host-arrival offsets; it covers selected system/RN/Appium diagnostics, not unrestricted App logs. The local-only capture child is reaped after the failure-status probe and before DELETE, without waiting for inherited pipe EOF or signaling the App/daemon. Its closed raw bytes, original identity and bounded arrival records are sealed and replay-checked separately from the original-PID dump and tag-mutation intents. Failure to confirm local retirement blocks release. It does not refresh/adopt an identity, enable Appium's own logcat capture, or infer handler execution, complete transport health or Close success from output/silence. On UI failure only, the same explicit diagnostic scope first probes the original UiAutomator2 `/status` once over a fresh direct connection before DELETE (at most two seconds, no proxy/retry/identity refresh), writing `platform/server-status.json`; `ready` or a timeout never proves retirement or changes the UI verdict. The same failure path then observes the existing `127.0.0.1:5037` daemon once via fixed read-only smart-socket requests, writing `platform/adb-transport.json`: protocol version, cached state, exact-serial transport selection, shell-service acceptance, and bounded boot-ID output are separate stages under one at-most-three-second I/O budget. No CLI version negotiation/autostart/kill, endpoint override, retry, settings or forwarding mutation is available. The probe shares the existing diagnostic window; failure is retained independently of the original UI error. Cached state/OKAY/boot comparison never grants authority or proves closure. Live capture stays open through both probes and is reaped before DELETE. Server-log/probe failure remains separate and cannot skip the other cleanup steps; optional observations share at most half the cleanup budget so their requested timeout does not consume the entire DELETE/helper/property-restoration window. Interruptions remain interruptions even if a post-read guard or receipt publication also fails. It is never implicitly enabled or an RF/session-authority API; uncertain restoration blocks phone release. Debug logs can contain UI text, capabilities and payload prefixes as well as screenshot/page data; all remain local and may be sensitive; see [pre-click evidence and HTTP retry budget](../../docs/testing/reports/2026-11-05-formal-android-preclose-evidence.md). Optional `--automation-idle-control --close-diagnostics` selects only fixed idle-page browsing under those same owners, with distinct `formal-android-managed-idle-control` bundle/CLI identity, empty startup snapshot and no Start/Close/scan; its success is not lifecycle success. Mutually exclusive `--automation-start-hold-control --close-diagnostics` instead selects Start once, one snapshot, a five-second quiet Current run window between bounded reads, then same-page Close, with no navigation/scan; its distinct `formal-android-managed-start-hold-control` scope/CLI key and sealed quiet-window record cannot be relabeled as lifecycle navigation evidence. Success retains Current run/closed. `formal-host-lifecycle-verify ATTEMPT` replays the recorded lifecycle or diagnostic scope's integrity offline without device commands or upgrading the pending host gate. See [managed entry usage](../../tests/consumers/react-native-bleng/README.md#managed-android-lifecycle) and [candidate limits](../../docs/testing/reports/2026-11-04-formal-android-managed-runner.md).
- Formal iOS scan candidate: `bleng_ios_candidate.IosCandidateOwner` owns one explicitly leased frozen-device-App install/launch and binds its receipts to the existing fresh native identity check. It rejects running old Apps, has no terminate/retry/console fallback, and permanently revokes provenance after detected drift. Its one-shot App finalizer composes with the existing observation lease: retain on success, fresh-identity-checked single PID termination on failure, quarantine uncertainty, and preserve primary/cleanup/publication errors. Cleanup has a separate deadline without reviving the scenario; PID-only termination is not an atomic boot-conditioned operation. This is not a CLI or a complete RF runner: WDA ownership, preflight, cross-resource finalization order, live cleanup validation and the final bundle are still required. See [candidate evidence and limits](../../docs/testing/reports/2026-11-04-formal-host-app-identity.md).
- Formal Android scan candidate: `bleng_android_candidate.AndroidCandidateOwner` validates a frozen APK with the pinned SDK, admits only single-user-0/non-shared-UID ownership, installs and cold-launches once through the shared guarded installer with an explicit root choice and no grants/fallback, and binds the installed hash plus original OS process identity. Its App-only finalizer composes with `AndroidRadioController.finish_app_observation`, not the old radio ON finalizer: success retains the App; failed or uncertain cleanup quarantines the lock. Package force-stop is not atomic with identity checks. A scoped managed-lifecycle device candidate now passed; it is not a scan/RF or complete outer-bundle verdict. See the [real lifecycle evidence](../../docs/testing/reports/2026-11-04-formal-android-managed-lifecycle.md).
- Managed Android automation now accepts a concrete `bleng_android_session.AndroidAutomationOwner`, not external readiness JSON or overridable Android callbacks. It rechecks live preparation, binds protected caps and the actual Appium endpoint/home/forward, correlates host/device session IDs with OS identity, and verifies idle/settings cleanup after a known DELETE. The supported profile must be explicitly prepared; it never installs, grants, roots or repairs in an ordinary run. Root is available, not a blocker. Bare `formal-host-ui android` remains refused without this owning-host handoff. The restricted real WebDriver lifecycle, binding, DELETE and helper restoration now have device evidence; scan/RF and full driver/config provenance remain unverified. Explicit helper rollback uses permission semantics rather than disappearance of an Android deny record, without relaxing the active-session baseline or UID-scope checks; see [managed lifecycle / restoration evidence and limits](../../docs/testing/reports/2026-11-04-formal-android-managed-lifecycle.md) and the [session contract](../../docs/testing/reports/2026-11-04-formal-android-session-owner.md).
- Android prepared-helper inventory: `bleng_android_automation.inspect_prepared_android_automation` inspects explicit helper candidates and installed hashes/UIDs, registration, old processes/forwarding and policy scopes under the real App-only phone lease. It is read-only, bounded and records reverse-sweep drift/failure evidence. `inventory-verified` still means `automation_admission=pending`: no session/Settings-service ownership, no finalizer and no automatic guard bypass. It is a preparation checkpoint, not a per-UI-read callback or new scan CLI. See [software evidence and remaining work](../../docs/testing/reports/2026-11-04-formal-android-automation-inventory.md).
- Formal automation ownership: `bleng_automation.ScanAutomationOwner` owns a nonce-routed local Appium child and one attach-only WebDriver session. Mandatory iOS platform callbacks cover WDA/forwarding; Android derives its callbacks only from the concrete owner. There is no default ready/no-op proof. Unknown session creation never triggers adoption or blind DELETE. An explicitly supplied `android_preparation=scope` also transfers temporary helper restoration to this owner: DELETE → server reap → platform finalizer → helper restore, with same-scope checks before spawn and restored-evidence checks in `require_closed()`. `None` denotes an externally preprovisioned baseline, not automatic setup. Server/session/platform/helper cleanup and evidence must finish before phone release; the restricted Android producer now has real lifecycle evidence; iOS concrete ownership, full provenance and RF remain pending.
- Prepared formal scan: `bleng_scan_runner.run_prepared_scan` consumes already-installed candidates, an attach-only driver, a live attested fixture and the same-run phone lease. It requires the managed automation owner, runs one shared scene, then automation (driver/server/platform and explicitly owned helper scope) → App → strict passive fixture → evidence → phone finalization. Cheap authority guards bracket UI I/O; fresh native identity is checked at entry/exit, clicks and operation completion. A session pass remains a pending outer host gate; this is not a live CLI or a replacement for automation ownership/full RF bundles. See [ownership architecture](../../docs/research/react-native/react-native-host-tooling-architecture.md#正式-typed-scan准备交接与执行阶段).
- Formal iOS compile: `bleng_ios_consumer` owns installed Podspec validation, the host's Nitro-free `PlatformContract` static target and its App/native-test build. Use `formal-host-ios-build`; it is source/local-package build evidence, not clean npm-artifact or runtime/RF evidence. There is no separate static Nitro consumer or second Node/Pod root. The safe-area 5.11.1 Pod lock and Simulator App/native-test build were refreshed through this owner; see [iOS build and helper-handoff evidence](../../docs/testing/reports/2026-11-04-formal-ios-build-automation-handoff.md), not an iOS runtime verdict.
- Full RF Lab: `run_rf_lab_full` → `rf_scenario_runner`.
- Standalone RecoveryTen: `run_rf_recovery_ten` → `rf_scenario_runner`.
- Pending read / real engine reload: `run_android_pending_read_reload` or `run_ios_pending_read_reload_gate` → `pending_read_reload_runner`; Android capture lives in `android_pending_reload_capture`.
- `rf_fixture` / `android_rf_host` own host-side fixture and installation/PID checks; the provider/session remains the live attestation authority.
- `capture_io` / `capture_transport` own bounded streams and SDK mechanics without recovery/pending protocol state. Scenario captures and ledgers own facts, ACK policy and semantic checks.
- `rf_suite_coordination` owns continuous10 marker mapping; `rf_attempt_finalizer` shares error/cleanup publication while the runner retains fixture ownership and signals.
- `rf_evidence_bundle` owns immutable artifact/evidence integrity.
- The superseded standalone continuous10 runners were removed; use `run_rf_lab_full`. Single-flow diagnosis remains available through `run_android_rf` / `run_ios_rf_scan`.
- The RN surface is **Tests** (category → scenario → setup) → **Current run** (one mounted scenario, preserved across view changes) → **Evidence** (technical identity, App failure and coverage limits). Ordinary `rf-workbench` launch creates no Probe and dispatches no BLE; explicit `basic` remains the ABI smoke route. Host-selected launches open their existing scenario, not a second execution path.
- [`rf_lab_catalog.ts`](../../tests/consumers/react-native-internal/src/rf_lab_catalog.ts) is display-only metadata for exact runtime/discriminator, platform, recipe and fixture needs, including planned/unsupported entries. `App.tsx` remains the execution router and existing runners retain lifecycle ownership. `rf_lab_session.tsx` projects only bounded reporter/computed-owner status, ignores raw event/resource/native identity records and keeps failure sticky until explicit manual begin. No core/runtime/mailbox/backend canonical state or new app/tool framework is added.
- Host tools own fixture/radio control, RF checks, cleanup and evidence. The App does not receive the final host physical/cleanup/bundle verdict; App Passed cannot stand in for host-gate Passed. See the [page/ownership boundaries](../../docs/research/react-native/react-native-rf-lab-test-architecture.md#rn-页面信息层级与职责).
- `run_android_adapter_transition` is an opt-in Android gate in the same App. The recipe is `pixi run just react-native host-android-rf-adapter-transition <device> <fixture_contract> <fixture_profile> [startup-off|active-loss]`; the final mode defaults to `startup-off`. Neither mode is implicit in full-suite. After the bounded `active-gatt-canonical-v1` audit fix and APK rebuild, a fresh **active-loss RF gate passed**, including host/physical/state/bundle checks and offline integrity verification; the original logcat-truncated attempt stays failed. See the [candidate-bound report](../../docs/testing/reports/2026-10-16-rn-android-active-read-radio-loss.md) for held + queued read settlement, the real 4s OFF deadline, pre-close retirement and fresh-Probe recovery. It does not prove in-flight write/CCCD loss, same-Hub recovery, permissions, iOS or later same-APK startup/full-suite runs.
- `run_android_permission_transition` is a separate opt-in host gate inside the same RN workbench: `pixi run just react-native host-android-rf-permission-transition <device> <fixture_contract> <fixture_profile>`. It runs denied startup, an active + queued read followed by permission revocation, and fresh-App RF recovery. The host must prove exact old-process `ApplicationExitInfo` reason 8; PID disappearance alone is insufficient. The dead Probe has no claimed close/zero result. Permission grants are restored before releasing the phone lease. `AndroidRadioController.finish_observation()` owns final read-only ON checking and release; the scenario runner does not finalize the controller's private state. There is no automatic retry or firmware flash. Offline bundle verification replays the shared ledger; software checks do not constitute RF evidence. The [root-controlled API 36 checkpoint](../../docs/testing/reports/2026-10-17-rn-android-permission-transition.md) records one complete fresh attempt with exact OS reason 8 and its candidate/coverage limits; earlier failed attempts remain failed. This is not same-Hub recovery, active write/CCCD loss or iOS permission coverage, and is not implicit in full-suite.
- The superseded local-HEX iPhone pending-reload entry is [archived](../archive/react_native/README.md) and removed from active Just recipes. Use `run_ios_pending_read_reload_gate`; the two evidence boundaries are not interchangeable.

The iOS `host-ios-device-permission-test` recipe stays in the existing XCUITest target and RN workbench; there is no new Python control runner. Its `permission-authorization` mode is explicitly **non-RF**, separate from Android's process-death gate. An optional restoration-only run has a distinct result scope and cannot count as a complete deny/restore pass. See the [iOS authorization checkpoint](../../docs/testing/reports/2026-10-17-rn-ios-permission-authorization.md).

The opt-in `host-ios-device-radio-control-test` also stays in that UI target; it is Settings-control feasibility, not an iOS adapter RF gate or a new App/Python runner. Initial ON, narrow accessibility selection, readback, restoration and unchanged native App identity are required; `inspect-only=1` cannot toggle or prove control. The [attempt history](../../docs/testing/reports/2026-10-17-rn-ios-radio-control-feasibility.md) preserves earlier initialization/navigation failures and a later non-RF ON→OFF→ON/same-native-App pass. Persistent result-page visibility after XCTest exit was not proved. Do not enable iOS adapter catalog/bundle support based on this control-only result.

The iOS startup-off candidate uses the same App and a narrow native launch/Linking gate. `ios_adapter_startup_journal` retains the original bounded native JSON bytes and a separate LF record projection; `ios_adapter_startup_ledger` audits cooperative native/JS identities, exact OFF DTOs, both 17-zero snapshots and the existing RF I/O transcript checker. The candidate `ios_adapter_startup_capture` now stages one opt-in XCTest window, reuses the bounded SDK transport and official install/PID/payload checks, and can download the exact run's journal after completion without App relaunch. The existing UI target owns Settings control/restoration and emits twelve identity-bound observations. Both lifetime and ready-boundary guards are mandatory; a caller must own phone/fixture/artifact installation. Xcode test execution itself may install the staged frozen App/runner. The parent `run_ios_adapter_startup` now connects the phone lease, in-process provider-local physical owner and the independent `ios-adapter-startup` evidence-bundle scenario; existing Android-only scenario restrictions remain unchanged. The explicit candidate recipe is `pixi run just react-native host-ios-rf-adapter-startup-candidate <udid> <prebuilt-app> <prebuilt-xctestrun> <contract> <profile> authorize-radio`. This is an authorization to mutate the radio once, not an ordinary build/test command. It has no build/provision fallback and is not part of full-suite. A fresh same-candidate signed device build must be checked before first real execution. Missing/untrusted final ON proof quarantines the phone lease without automatic unlock or stale adoption. Software/complete synthetic-bundle checks have passed, but the actual whole SDK/RF path has not been run. Neither capture nor ledger alone proves Settings state, independent process provenance or RF. Default UI discovery skips this gate; timeout/runner death does not guarantee radio restoration. The cross-layer sample `tests/support/rf_lab/ios_adapter_startup_journal.json` is an unmodified simulator NativeTests attachment, not device evidence; its origin/hash and validation commands are in the same report. iOS active-loss remains unsupported.

Tests live in [`../tests/react_native/`](../tests/react_native/). Choose **one** hardware-free Python entry below; neither needs devices, SDK installation, npm or Pods:

```text
# RN tooling-only subset:
pixi run just react-native tools-test
# OR combined tooling + provider + Android permission/radio controller tests:
pixi run just react-native tools-fixture-test
```

The combined command includes the entire `tools-test` subset in one process. Do not run the subset again after the combined command. Synthetic support must never be imported by a live runner/provider or counted as RF evidence. Ordinary RF runs never flash firmware.

For all maintained host Jest suites, after host npm dependencies are installed, run:

```text
pixi run just react-native host-test
# Inspect the same entry's actual discovery without executing tests:
pixi run npm --prefix tests/consumers/react-native-internal test -- --listTests --json
```

`host-test` calls the host package's `test` script (`jest --runInBand`) once using the existing Jest configuration. It does not chain the three overlapping REJECT scripts. Keep `test:ui`, `test:write-reject`, `test:ccc-enable-reject` and `test:ccc-disable-reject` for targeted diagnosis; do not rerun them after the total entry just to repeat coverage. Current discovery includes 17 suites (`*.test.ts` / `*.test.tsx`); the existing `App.ledger.test.cjs` was not wired into the old entries and remains outside this discovery, unchanged with its unique assertions preserved. Jest results are not native runtime, device or RF evidence.

See the [ownership, support design and consolidation limits](../../docs/research/react-native/react-native-host-tooling-architecture.md). The core restructuring is complete; further generic tool/framework work is deferred unless a product requirement or observed failure justifies it. Stable CLI names do not imply that a CLI module should own shared implementation.
